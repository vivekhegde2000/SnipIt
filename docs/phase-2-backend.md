# Phase 2 — Backend, Accounts and Sync

**Goal:** optional user accounts so snippets sync across devices and are backed up in the cloud,
while the app stays **local-first**: instant, and fully usable offline or without an account.
**Estimate:** ~4–6 days (written for someone new to backend development).
**Location:** `apps/api`, plus small additions to `apps/web` and `packages/shared`.

Back to [plan index](README.md) · Previous: [Phase 1 — Frontend](phase-1-frontend.md)

---

## 1. Scope

| # | Feature | Details |
|---|---|---|
| B1 | **Register / login / logout** | Email + password. Session is a JWT in an httpOnly cookie. |
| B2 | **Guest mode stays** | Without an account the app behaves exactly like Phase 1. |
| B3 | **First-login upload** | Existing local snippets and collections are uploaded to the account automatically. |
| B4 | **Multi-device sync** | Changes made offline sync when back online. Last-write-wins conflict handling. |
| B5 | **Sync status UI** | Indicator: "Synced ✓", "Syncing…", "Offline", "Sync error · Retry". |
| B6 | **REST API** | CRUD endpoints for snippets and collections (useful for learning, testing and future clients). |
| B7 | **Account settings** | Change password, delete account (deletes all server data), sign out. |

Out of scope: OAuth/social login, email verification, password reset by email, sharing between users.
These are possible later additions.

## 2. Architecture

```
 Browser (PWA)                         Netlify (static + proxy)           Render (free)          Neon (free)
┌──────────────────────────┐          ┌─────────────────────────┐      ┌──────────────────┐   ┌─────────────┐
│ React UI                 │          │ /*      → index.html    │      │ Express 5 API    │   │ PostgreSQL  │
│   ↕ hooks (useLiveQuery) │  HTTPS   │ /api/*  → proxy ────────┼─────▶│ routes→services  │──▶│             │
│ IndexedDB (Dexie)  ◀─────┼── sync ──┼─────────────────────────┤      │ Prisma Client    │   │             │
│ Sync engine              │          └─────────────────────────┘      └──────────────────┘   └─────────────┘
└──────────────────────────┘
```

**Key idea: same origin through the Netlify proxy.** The browser only ever talks to
`https://snipit.netlify.app`; Netlify forwards `/api/*` to Render. This means:
- **no CORS setup** in production,
- the auth cookie is **first-party** (`SameSite=Lax`), so it isn't blocked by third-party-cookie protections in Safari, Chrome or Firefox,
- the frontend just calls `fetch('/api/...')`.

In local development the Vite dev server proxies `/api` to `http://localhost:4000` in the same way.

```ts
// apps/web/vite.config.ts
server: { proxy: { '/api': 'http://localhost:4000' } }
```

```toml
# netlify.toml — add ABOVE the SPA fallback rule
[[redirects]]
  from = "/api/*"
  to = "https://<your-api>.onrender.com/api/:splat"
  status = 200
  force = true
```

## 3. Database (Prisma + PostgreSQL)

### 3.1 Schema — `apps/api/prisma/schema.prisma`
```prisma
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
  // The connection URL is configured in prisma.config.ts (Prisma 7+) from env vars.
}

model User {
  id           String       @id @default(uuid())
  email        String       @unique
  passwordHash String
  name         String?
  createdAt    DateTime     @default(now())
  updatedAt    DateTime     @updatedAt
  snippets     Snippet[]
  collections  Collection[]
}

model Collection {
  id        String    @id                 // UUID generated by the client
  userId    String
  user      User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  name      String
  color     String
  icon      String?
  sortOrder Int       @default(0)
  createdAt DateTime
  updatedAt DateTime                      // client edit time → used for conflict resolution
  deletedAt DateTime?                     // tombstone, so deletes sync too
  syncedAt  DateTime  @updatedAt          // server write time → used as the sync cursor
  snippets  Snippet[]

  @@index([userId, syncedAt])
}

model Snippet {
  id           String      @id            // UUID generated by the client
  userId       String
  user         User        @relation(fields: [userId], references: [id], onDelete: Cascade)
  collectionId String?
  collection   Collection? @relation(fields: [collectionId], references: [id], onDelete: SetNull)
  title        String
  content      String
  description  String?
  language     String      @default("plaintext")
  tags         String[]
  isFavorite   Boolean     @default(false)
  copyCount    Int         @default(0)
  lastCopiedAt DateTime?
  createdAt    DateTime
  updatedAt    DateTime
  deletedAt    DateTime?
  syncedAt     DateTime    @updatedAt

  @@index([userId, syncedAt])
  @@index([userId, collectionId])
}
```

**Why two timestamps?**
- `updatedAt` is when the user edited the record (set by the client). It decides **who wins a conflict**.
- `syncedAt` is when the server stored it (set by Prisma). It is the cursor for "**what changed since my last sync?**".
  Using server time for the cursor avoids bugs caused by devices whose clocks are wrong.

> Prisma's setup changes between major versions. Follow the current Prisma "Getting started with
> PostgreSQL" guide when installing; with Prisma 7 the DB URL lives in `prisma.config.ts` and the client
> uses the `@prisma/adapter-pg` driver adapter.

### 3.2 Environments
| Env var | Example | Used for |
|---|---|---|
| `DATABASE_URL` | `postgresql://snipit:snipit@localhost:5432/snipit` | App connection (on Neon, use the **pooled** URL) |
| `DIRECT_URL` | Neon **direct** (non-pooled) URL | Running migrations |

missing. Commit an `.env.example` and **never** commit `.env`.

## 4. API design

Base path `/api`. JSON in and out. Every request body and query is validated with zod.
Errors always use one shape:
```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Title is required", "details": { } } }
```

### 4.1 Endpoints
| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/api/health` | – | Liveness check (also used by Render) |
| POST | `/api/auth/register` | – | `{ email, password, name? }` → creates user, sets cookie |
| POST | `/api/auth/login` | – | `{ email, password }` → sets cookie |
| POST | `/api/auth/logout` | ✓ | Clears cookie |
| GET | `/api/auth/me` | ✓ | Current user (or 401) |
| PATCH | `/api/auth/password` | ✓ | `{ currentPassword, newPassword }` |
| DELETE | `/api/auth/account` | ✓ | Deletes the user and all data (cascade) |
| GET | `/api/snippets` | ✓ | List (`?collectionId=&tag=&q=&includeDeleted=`) |
| POST | `/api/snippets` | ✓ | Create |
| GET | `/api/snippets/:id` | ✓ | Get one |
| PATCH | `/api/snippets/:id` | ✓ | Partial update |
| DELETE | `/api/snippets/:id` | ✓ | Soft delete (sets `deletedAt`) |
| GET / POST | `/api/collections` | ✓ | List / create |
| PATCH / DELETE | `/api/collections/:id` | ✓ | Update / soft delete |
| POST | `/api/sync` | ✓ | **Push local changes and pull remote changes in one call** (see §5) |

Status codes: `200` OK, `201` Created, `204` No Content, `400` validation, `401` not logged in,
`403` not your record, `404` not found, `409` conflict (e.g. email taken), `429` rate limited, `500` unexpected.

Every query is **scoped by `userId`** from the session. Users can never read or write another user's rows.

## 5. Sync design (local-first, last-write-wins)

### 5.1 Client changes (Dexie schema version 2)
- Add a local-only `dirty: 0 | 1` field to `snippets` and `collections` (indexed).
  Every local create, update or delete sets `dirty = 1`.
- Add a `meta` entry `lastSyncCursor` (an ISO timestamp from the server; `null` means never synced).
- Deletes stay **soft** (`deletedAt`), so they can be synced. Tombstones older than 30 days and already synced can be purged.

### 5.2 The `/api/sync` contract
```ts
// Request
{
  cursor: string | null,                     // last cursor from the server
  changes: { snippets: Snippet[], collections: Collection[] }   // all dirty records
}
// Response
{
  cursor: string,                            // new cursor to store
  changes: { snippets: Snippet[], collections: Collection[] },  // server changes since old cursor
  rejected: { id: string, reason: string }[] // e.g. invalid data
}
```

### 5.3 Server algorithm (inside one transaction)
1. For each incoming record (collections first, then snippets):
   - If a row with that `id` exists but belongs to **another user**, reject it.
   - If it doesn't exist, **insert** it.
   - If it exists and `incoming.updatedAt > existing.updatedAt`, **update** it (the incoming edit is newer, so it wins).
   - Otherwise **skip** it (the server copy is newer and will be sent back in step 2).
2. Select every row for this user where `syncedAt > cursor` (or everything if `cursor` is null).
3. Return those rows plus `cursor = now()` captured at the **start** of the transaction. Overlapping
   rows may be re-sent next time, which is harmless because applying them again changes nothing.

### 5.4 Client algorithm
1. Read all `dirty` rows and POST them with the stored cursor.
2. Apply the returned `changes` to Dexie, but only where `remote.updatedAt >= local.updatedAt`.
   A local row that was edited again *during* the request keeps `dirty = 1`.
3. Clear `dirty` on the pushed rows that weren't edited during the request.
4. Save the new cursor.

**When to sync:** on app start, after login, on `online` events, on window focus, 2 s after any local
change (debounced), and every 5 min while visible. One sync runs at a time, and failures retry with backoff
(2 s, 4 s, 8 s … up to 5 min).

**On logout:** ask "Keep a copy of your snippets on this device?" If not, clear the local DB.
**Switching accounts** on the same device clears local data first, so accounts never mix.

> Last-write-wins is simple and suits a personal snippet tool. The rare cost: if the same snippet is edited
> on two offline devices, the later edit wins entirely. That's acceptable for this app and noted in the README.

## 6. Authentication and security

| Topic | Approach |
|---|---|
| Passwords | `bcryptjs` with cost 12. Minimum 8 characters. Never logged or returned. |
| Session | JWT `{ sub: userId }` signed with `JWT_SECRET`, 7-day expiry, in cookie `snipit_session`: `httpOnly`, `secure` (in production), `sameSite: 'lax'`, `path: '/'` |
| CSRF | Same-origin setup + `SameSite=Lax` + the API only accepts `application/json` bodies |
| Rate limiting | `express-rate-limit`: about 10 requests/min per IP on `/auth/login` and `/auth/register`, plus a generous global limit |
| Headers | `helmet()` |
| Proxies | `app.set('trust proxy', …)` so client IPs and secure cookies work behind Netlify and Render (verify the right hop count when deploying) |
| Input | zod on every body, query and param; max request body size of 2 MB (`express.json({ limit: '2mb' })`) |
| Data access | Every Prisma query filters by `userId` |
| Errors | The central error handler hides stack traces in production; generic "Invalid email or password" message (don't reveal which one was wrong) |
| Secrets | Only in env vars (`.env` locally, the Render dashboard in production) |

Express 5 forwards errors from `async` route handlers to the error middleware automatically, so you don't
need `try/catch` in every route.

## 7. Folder structure (`apps/api`)

```
apps/api/
├─ prisma/
│  ├─ schema.prisma
│  └─ migrations/
├─ prisma.config.ts
├─ src/
│  ├─ config/env.ts              # zod-validated env vars
│  ├─ lib/
│  │  ├─ prisma.ts               # single PrismaClient instance
│  │  ├─ jwt.ts                  # sign / verify helpers
│  │  └─ password.ts             # hash / compare
│  ├─ middleware/
│  │  ├─ requireAuth.ts          # reads cookie → req.userId, or 401
│  │  ├─ validate.ts             # validate({ body, query, params }) with zod
│  │  ├─ errorHandler.ts         # AppError → JSON error shape
│  │  └─ notFound.ts
│  ├─ modules/
│  │  ├─ auth/        auth.routes.ts  auth.controller.ts  auth.service.ts
│  │  ├─ snippets/    snippets.routes.ts  snippets.controller.ts  snippets.service.ts
│  │  ├─ collections/ collections.routes.ts  ...
│  │  └─ sync/        sync.routes.ts  sync.service.ts
│  ├─ app.ts                     # builds the express app (exported for tests)
│  └─ server.ts                  # app.listen(PORT)
├─ tests/                        # *.test.ts with Supertest
├─ .env.example
├─ docker-compose.yml
├─ package.json                  # name: @snipit/api
└─ tsconfig.json
```

**Layering rule:** *routes* (URL + middleware) → *controller* (reads `req`, sends `res`) →
*service* (business logic + Prisma). Services never touch `req`/`res`, which makes them easy to test.

Scripts:
```json
{
  "dev": "tsx watch src/server.ts",
  "build": "tsup src/server.ts --format esm",
  "start": "node dist/server.js",
  "test": "vitest",
  "db:migrate": "prisma migrate dev",
  "db:deploy": "prisma migrate deploy",
  "db:studio": "prisma studio"
}
```
`tsup` bundles `packages/shared` into the output, so the production server has no TypeScript runtime dependency.

### 10.2 API — Render (free web service)
| Setting | Value |
|---|---|
| Root directory | repo root (monorepo) |
| Build command | `npm ci && npm run build -w @snipit/api && npm run db:deploy -w @snipit/api` |
| Start command | `npm run start -w @snipit/api` |
| Health check path | `/api/health` |
| Env vars | `DATABASE_URL`, `DIRECT_URL`, `JWT_SECRET`, `NODE_ENV=production` |

> ⚠️ **Free tier sleeps after ~15 min idle**, and the first request then takes ~30–60 s to wake.
> Because the app is local-first, the UI never waits for this: the sync indicator shows "Syncing…" and
> retries until the server responds.

### 10.3 Frontend — Netlify
Add the `/api/*` proxy redirect (see §2) **above** the SPA fallback in `netlify.toml`, then redeploy.
